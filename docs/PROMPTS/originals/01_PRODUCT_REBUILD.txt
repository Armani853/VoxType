- RAM.
- Thread count.
- Queue depth.
- Disk usage.
- RTF.
- WER/CER.
- Model loading time.
- UI responsiveness.
- Memory growth over time.

Проведи длительный soak-тест, включая минимум 60 минут или более строгий срок из исходного ТЗ.

Выполни повторные запуски и остановки.

Проверь производительность после длительной работы.

Используй реальные wall-clock измерения.

Не подменяй часовой тест быстрым циклом синтетических данных.

Не утверждай отсутствие утечек только потому, что финальная память ниже максимальной.

Проверяй устойчивый тренд, пиковые значения, освобождение ресурсов и повторяемость результата.

Если обнаружены серьёзные проблемы — устрани их и повтори измерения.

## 12. ДЕСЯТЫЙ ЭТАП — НЕПРЕРЫВНЫЙ ЦИКЛ ИСПРАВЛЕНИЯ

Это обязательный режим работы.

Ты должен организовать процесс:

**OBSERVE → REPRODUCE → DOCUMENT → PRIORITIZE → FIX → TEST → BUILD → COMPUTER USE RETEST → REGRESSION → REPEAT**

Для каждой итерации:

1. Выбери группу дефектов.
2. Подтверди воспроизведение.
3. Зафиксируй исходное состояние.
4. Установи root cause.
5. Выполни исправление.
6. Добавь регрессионные тесты.
7. Выполни статический анализ.
8. Выполни релевантные автоматические тесты.
9. Запусти программу.
10. Проверь исправление через Computer Use.
11. Проверь соседние функции.
12. Обнови журнал дефектов.
13. Сохрани evidence.
14. Перейди к следующим проблемам.

**После любой существенной правки интерфейса необходимо снова смотреть на работающий интерфейс.**

После исправления нескольких дефектов проводи полный regression smoke.

После крупных изменений пересобирай release-кандидат.

Не проверяй старый бинарник после изменения исходного кода.

### Правило итераций

Не устанавливай искусственный лимит в 2–3 цикла.

Количество итераций определяется количеством оставшихся проблем и реально доступными ресурсами.

Не прекращай работу только потому, что прошли существующие тесты.

Продолжай в рамках текущей доступной сессии и инструментов, пока есть воспроизводимые существенные дефекты, которые можно исправить и перепроверить.

Если среда ограничивает продолжительность работы, сохрани точное состояние, открытые дефекты и воспроизводимые команды. Не обещай самостоятельного продолжения после завершения сессии без реально настроенного механизма выполнения.

## 13. ПРАВИЛО НУЛЕВОЙ ТЕРПИМОСТИ К КРИТИЧЕСКИМ ДЕФЕКТАМ

Release не может быть одобрен, если присутствует хотя бы один подтверждённый нерешённый P0 или P1.

P0:

- Потеря данных без предупреждения.
- Серьёзное нарушение безопасности.
- Невозможность запуска.
- Повреждение пользовательских файлов.
- Невозможность выполнить основную функцию.
- Критическое зависание или crash.

P1:

- Основной сценарий работает нестабильно.
- Некорректная вставка текста в поддерживаемое приложение.
- Потеря фокуса, приводящая к неверному действию.
- Некорректная работа важных настроек.
- Систематическое ухудшение производительности.
- Значимая неисправность onboarding.
- Необъяснимые состояния.
- Существенные дефекты UI.

P2 и P3 оценивай по влиянию на готовность продукта.

Не скрывай и не понижай приоритет дефекта ради прохождения release gate.

## 14. НЕЗАВИСИМЫЕ АУДИТЫ

Если поддерживаются subagents или параллельные исполнители, организуй независимые проверки.

Направления:

**Agent A — UX/UI**

Исследует пользовательские сценарии, визуальные дефекты, понятность интерфейса и accessibility.

**Agent B — Audio/ASR**

Исследует распознавание, буферизацию, производительность и обработку ошибок.

Если настоящие независимые агенты недоступны, выполни эти проверки последовательно с отдельными отчётами.

Не называй собственную повторную проверку независимой.

После каждого крупного цикла привлекай независимый review, если среда это поддерживает.

## 17. RELEASE ACCEPTANCE GATES

Объявлять выпуск готовым разрешается только после выполнения всех обязательных условий.

### Gate A — Specification

Все обязательные пункты исходного ТЗ реализованы либо имеют явно согласованное исключение.

### Gate B — Functional

Все критические пользовательские сценарии проверены.

### Gate C — UX/UI

Основные экраны и состояния исследованы через Computer Use, существенные проблемы исправлены.

### Gate D — Stability

Все необходимые reliability, fault-injection и soak-тесты выполнены.

### Gate E — Windows Integration

Поддерживаемые приложения, focus, hotkeys, overlay и вставка проверены.

### Gate F — Security

Нет известных критических проблем безопасности и приватности.

### Gate G — Installer

Собранный release-кандидат проверен после установки.

### Gate H — Regression

Полный релевантный набор автоматических и GUI-регрессионных тестов пройден.

### Gate I — Documentation

Пользовательские и технические документы соответствуют фактическому продукту.

### Gate J — External Acceptance

Отдельно подтверждены необходимые внешние проверки, включая физически чистый Windows-ПК и живую диктовку, если они обязательны по исходному ТЗ.

Если какой-либо Gate не выполнен, выпуск остаётся `NOT APPROVED` или `CONDITIONALLY READY`, но не `PRODUCTION APPROVED`.

Никогда не объявляй «без единой ошибки» как абсолютный факт. Вместо этого сообщай, какие классы дефектов проверены, какие остались неизвестными и какие критерии пройдены.
