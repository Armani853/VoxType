The development path already has `scripts/run.ps1`, `scripts/lint.ps1` and `scripts/test.ps1`; only release packaging needs Nuitka. `scripts/build_portable.ps1` removes its build root before compiling, but retained stats show 99.66–100.00% C cache hits, so the compiler cache persists despite clearing this root. The completed XML report identifies 176.06 s in Nuitka optimization and 29.77 s in C generation, a combined 205.83 s before attributing MSVC, link or copy. Its largest per-module optimization entries include `tomllib._parser` (5.281 s), `huggingface_hub.hf_api` (3.156 s), `urllib.request` (2.766 s) and `numpy.f2py.crackfortran` (2.625 s); no exclusion is justified by these timings alone. `nuitka5` generated 592 module C files, including 35 `anyio` and 9 `faster_whisper` modules; no compiled module name began with pytest, `_pytest`, ruff, mypy, nuitka or tests. Transitive `anyio` alone does not establish bloat. The current report confirms MSVC and a complete standalone EXE but not separately timed compile/link/copy or total wall time, because the parent measurement session was interrupted. `scripts/build_portable.ps1` now requests `--report=<build>/nuitka-compilation-report.xml` and prints total Nuitka wall time in future required release builds. This is instrumentation, not a measured speedup. Nuitka's [official user manual](https://nuitka.net/user-documentation/user-manual.html) describes report timings and cache statistics; its [cache guidance](https://ftp.nuitka.net/user-documentation/tips.html) says MSVC `clcache` is integrated automatically. Do not change jobs, cleanup or hidden imports without matched measurements and packaged regression.

Python coordinates UI, audio queues, state transitions and formatting, while PySide6/Qt paint, PortAudio capture, ONNX VAD and CTranslate2 inference run substantially in native libraries. The precise CPU time split is **not measured**. No Rust/C++ module or PySide6 migration is justified by current evidence. A Qt rewrite would increase packaging and regression scope without a demonstrated user benefit. Measure a specific CPU-bound Python hot path before any native prototype.

Targets remain: first visible content ≤700 ms; ordinary UI p95 ≤50 ms; Settings ≤150 ms; idle close ≤1 s; no unexplained GUI stall >200 ms; responsive UI under maximum ASR. No target is marked PASS solely from a source test or one smoke measurement. Matched installed-EXE before/after and Nuitka compilation report remain required.

## Source optimization after the baseline, pending a new release build

Profiling a native Qt application with `MainWindow` and `SettingsWindow` found 20 repeated `apply_theme(SYSTEM)` calls took a median **159.573 ms**, p95 **223.381 ms** and maximum **1045.298 ms**. The previous settings-save path applied the entire QSS even when the theme had not changed. `DesktopApplication._save_settings` now applies it only on a real theme change, and similarly avoids redundant hotkey registration, audio/VAD factory recreation and language/hotkey label refresh for unrelated settings. This targets a measured GUI-thread cost; the total settings-save latency on a final installed build is still unmeasured.

At idle, the 50 ms poll previously rewrote MainWindow, tray and overlay on every identical snapshot. In a 30-repeat native Qt microbenchmark of MainWindow plus overlay, the median redundant update was **0.603 ms** (p95 **1.092 ms**). The changed-snapshot guard took **0.001 ms** median (p95 **0.007 ms**) for the same unchanged data. This removes up to roughly 20 redundant render passes per idle second in that scenario. Active snapshots still advance and continue to render; target acquisition and other poll side effects still run. This is a measured micro-operation improvement, not a claimed 603× improvement in whole-app performance.

`scripts/workflow.ps1` now exposes DEV, QA, RELEASE and Auto modes. Auto chooses QA for code/config changes and does no runtime rebuild for documentation-only changes. RELEASE requires a clean committed worktree, runs lint and tests once, then passes `-SkipChecks` to `build_installer.ps1`/`build_portable.ps1`; direct installer invocation keeps its normal checks. Thus a repeated lint/test pass is removed from the combined release command without disabling the acceptance gates. The QA workflow completed Ruff, mypy and **264 passed / 5 deselected** in **34.142 s** for tests, lint **1.605 s**; the known Windows `0x8001010d` diagnostic still appeared. Three new fast-path unit cases passed. One source GUI interaction via Computer Use showed the no-model state, saved `minimize_to_tray: false` in an isolated profile and exited by X. The `sky.click` return for Save was 185.6 ms **including automation overhead**, so it is not used as an application latency SLO. No post-change Nuitka build has been made because the code changes are still being consolidated.

## Source startup iteration, 2026-11-07

The initial source smoke (`build/qa-source-fastpath-20261106/data/logs/voxtype.log`) measured `shell_ready` at 1508.2 ms and first content paint 1481.7 ms after `MainWindow` construction. Profiling showed hidden `DictationOverlay.set_compact()` called `adjustSize()` before the overlay was visible; this took roughly 0.7 s in an isolated constructor profile. ### Measured root cause and second source iteration

A native Qt event-profile harness (`QApplication.notify` timing, isolated source process) attributed a 608.4 ms first-event-loop block to a hidden `DictationOverlay` `PolishRequest`; nested label `FontChange` took 608.1 ms. Overlay construction was therefore moved to its first active use, with signal connections created once and no overlay object or polish during idle startup. This differs from merely omitting `adjustSize`: Qt had still polished the preconstructed hidden window later. A new isolated `--ui-smoke-test` (`build/qa-source-overlay-lazy-20261107`) measured `shell_ready` **221.9 ms** and first content paint **188.7 ms** after `MainWindow` construction. These are one source run, exclude process/import time, and do not establish the installed-EXE ≤700 ms target.

The same run exposed a separate **1000 ms UI stall** while first-run onboarding was constructed (893.7 ms). cProfile on a representative native Qt window attributed roughly 0.62 s initially to `QWizard.setWizardStyle(ModernStyle)` even though Windows Qt already used that style. After guarding that redundant call, the first native wizard `setOption` still consumed 0.66 s, and three sequential wizard constructions took **434.0, 8.1, 9.5 ms**. This is one-time native Qt wizard initialization, not a Python loop. The next source smoke (`build/qa-source-modern-style-20261107`) had `shell_ready` **613.7 ms**, first content paint **618.9 ms**, and first-run onboarding construction **582.9 ms** with a **672 ms UI stall**. The large run-to-run variation and the onboarding stall remain unresolved; no final SLO is declared.

An onboarding device refresh also silently emitted `microphone_selected` for the already-selected device, starting an unsolicited two-second audio test. During a timed shutdown that worker tried to emit to a deleted Qt signal object and raised `RuntimeError`. `set_microphones()` now updates the selection without emitting a user-selection signal; changing the combo box still emits it. A targeted regression test covers two programmatic refreshes and one real selection. The related audio worker shutdown race still requires a separate ownership review; this change removes the automatic trigger, not every possible in-flight test.

The first `scripts/workflow.ps1 -Mode Dev -Diagnostics` attempt failed with `No module named voxtype`; `scripts/run.ps1` lacked `PYTHONPATH=src`. That launch path is fixed and an actual DEV diagnostics run completed with exit code 0 in **18.706 s** (one run on this machine). Diagnostics imports heavy native libraries and is not the typical GUI hot cycle. QA mode passed Ruff, mypy, **266 tests / 5 deselected** before the latest overlay/onboarding change; after that change, targeted tests passed and the full suite later passed **268 tests / 5 deselected**. The full suite must be rerun if packaging code changes again before release.

Release artifact names now include the source commit and refuse to replace an existing release for the same commit. The old fixed-name portable ZIP and installer remain untouched. This protects the only retained candidate while allowing one fresh build after code freeze; it has not yet been exercised in a full release run.
