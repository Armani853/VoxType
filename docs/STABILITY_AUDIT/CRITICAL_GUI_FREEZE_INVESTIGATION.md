# VoxType — расследование P0: пустое окно и зависание GUI

Дата: 2026-11-05. Статус: **NOT READY FOR COMMERCIAL DELIVERY** до выяснения первопричины чёрного/белого экрана и ручной приёмки неохваченных аппаратных сценариев.

## Исходные симптомы

В обращении пользователя приложены два скриншота: (1) окно VoxType с полностью чёрной областью содержимого, (2) с полностью белой областью. Также сообщены непредсказуемые зависания и невозможность завершить приложение крестиком. Это реальные пользовательские наблюдения; в текущем автоматизированном окружении именно чёрный/белый кадр пока не воспроизведён. Изображения доступны в исходном сообщении обращения; отдельных файловых путей к ним среда не предоставила.

В журнале действующей пользовательской установки `C:\Users\Алла\AppData\Local\VoxType\VoxType\Logs\voxtype.log` обнаружены независимые исторические `UI_STALL`, включая 8360 мс 2026-10-09 в состоянии `COMPLETED`. Очень большие интервалы через часы сна Windows нельзя интерпретировать как непрерывный GUI freeze; причинная связь этих записей с двумя скриншотами не установлена.

Windows Application Event Log независимо содержит `Application Hang` (Event ID 1002) и `AppHangB1` (WER Event ID 1001) для `VoxType.exe` 2026-11-04 в 23:48:56, а также 2026-11-05 в 00:50:06. WER-подпись P3 `6a6a51ed` соответствует PE-времени 2026-07-29, то есть старому бинарнику пользовательской установки, а не новому тестовому EXE. Это подтверждает реальные остановки взаимодействия с Windows. Доступ к `C:\ProgramData\Microsoft\Windows\WER\ReportArchive\Critical_VoxType.exe_*` текущему процессу запрещён, поэтому стеки из WER-архива извлечь не удалось; без них нельзя доказать конкретную функцию, блокировавшую GUI в этих эпизодах.

## Среда и метод

- Windows 11 10.0.26200, Python 3.12.7, PySide6, VoxType 0.2.4.
- Исходники: `C:\Dev\Projects\AI\Voice-recognizer`. До начала изменений Git был чистым. Существующий установленный EXE: `C:\Users\Алла\AppData\Local\Programs\VoxType\VoxType.exe`; процесс пользователя не завершался принудительно и установка не перезаписывалась.
- Computer Use недоступен в этой сессии: требуемый skill-интерфейс `node_repl` отсутствует среди доступных инструментов. Использованы настоящая Windows GUI-сессия, PySide6 `QScreen.grabWindow(HWND)`, Win32/Qt-проверки, пиксельная выборка, `first_content_paint` и проверка отсутствия оставшихся потоков.
- Изолированные `VOXTYPE_DATA_DIRECTORY` и `VOXTYPE_CACHE_DIRECTORY` применены для GUI стресс-сценариев с моделью/аудио; тест доступной модели читал установленную локальную модель `small` из пользовательского каталога, не записывая в него.
- В приложении нет QWebEngine. Центральный widget — `QScrollArea` с canvas; его геометрия и первый paint теперь регистрируются.

## Воспроизведение и подтверждённые причины

1. **Оставшийся процесс после крестика при отключённом «сворачивать в трей».** `MainWindow.closeEvent` принимал событие закрытия, но `QApplication.setQuitOnLastWindowClosed(False)` оставлял event loop и tray-процесс. Исправлено: крестик в этом режиме посылает `exit_requested`, приложение выполняет свой асинхронный shutdown и только потом закрывает окно. При включённой настройке крестик по-прежнему сворачивает в трей — это ожидаемое поведение, выход выполняется через меню трея.
2. **Выход с ещё работающей загрузкой модели.** До исправления инструментированный сценарий `--slow-model-load-ms 3000 --close-delay-ms 200` завершился с `closed=true`, но `live_voxtype_threads=["voxtype-session-starter"]`. `shutdown()` не отслеживал starter/preloader и мог закрыть backend/SQLite раньше их работы. Теперь `shutdown()` дожидается их с ограниченным таймаутом и не заявляет успешное освобождение при живом worker. Повтор того же GUI-сценария: `live_voxtype_threads=[]`, `closed=true`.
3. **Невосстановимое `STARTING` после ошибки аудиоустройства при создании capture.** Инъекция `OSError("synthetic test audio device disconnect")` воспроизвела `InvalidStateTransition: Forbidden transition starting -> error_recoverable`; интерфейс оставался в `STARTING`. Разрешён этот переход в state machine. Повторный GUI-сценарий показал `ERROR_RECOVERABLE`, нарисованный интерфейс и чистый выход.
4. **Ложноположительный packaged smoke-test.** При уже работающем VoxType `--ui-smoke-test` мог только активировать старый экземпляр и вернуть 0; кроме того, прежний smoke вызывал `QApplication.quit` до завершения фонового shutdown. Изолированный smoke теперь обходит singleton только при явном тестовом каталоге, проверяет пиксели/первый paint и вызывает `shell.quit`. Сборочный скрипт задаёт отдельный тестовый профиль.
5. **Повторная полировка QSS 40 раз/с.** `update_snapshot()` безусловно вызывал `unpolish/polish` двух widget при каждом 50-мс тике. Теперь это происходит только при смене соответствующего dynamic property. Это подтверждённая избыточная работа GUI, но причинная связь с чёрным/белым экраном **не доказана**.
6. **Ошибка самого GUI smoke в сборочном скрипте.** Скрытый запуск (`-WindowStyle Hidden`) вместе с `QT_QPA_PLATFORM=offscreen` не позволяет проверить настоящий Windows paint. На собранном EXE скрытый запуск дал `colors=1, first_paint=False, exit=3`, тот же EXE с видимым окном дал `colors=15, first_paint=True, exit=0`. Поэтому сборочный smoke теперь запускается видимо на Windows и использует изолированный профиль. Это не считается воспроизведением исходной жалобы при обычном запуске.

Для собственно чёрного/белого кадра root cause не установлена. Принудительные `repaint()`/`processEvents()`, бесконечные retry и `os._exit()` не применялись.

## Инструментирование

Журнал содержит миллисекундные timestamps и `startup_stage` для загрузки конфигурации/SQLite/устройств, создания окон, применения QSS, `show`, запуска таймеров и входа/выхода Qt event loop. `first_content_paint` фиксирует размеры viewport/canvas. `UI_POLL_SLOW` разбит на target/snapshot/widgets/other; отдельно регистрируются `UI_DISPATCH_SLOW`, `UI_STALL`, длительные GUI callbacks и исключения shutdown worker. Watchdog стартует **до показа главного HWND и трея**, чтобы захватить раннее зависание до входа в event loop. При задержке >2 с он однократно пишет `UI_STALL_STACK` со стеком GUI-потока без текста диктовки или PCM. Это подтверждено контролируемой 2200-мс блокировкой обычного GUI callback (`profile-watchdog-stack/logs/voxtype.log`) и отдельно `TrayController.show` до первого paint (`profile-tray-show-block/logs/voxtype.log`): стек в обоих случаях указал на точную тестовую функцию. Это не доказывает, что реальный старый AppHang был вызван треем. Один пример: `profile-baseline/logs/voxtype.log` — загрузка настроек 1,6 мс, открытие SQLite 10,7 мс, перечисление устройств 10,8 мс, главное окно 377,8 мс, вспомогательные окна 993,9 мс, QSS 79,0 мс, `show` 72,4 мс, первый paint примерно через 1,57 с после начала построения UI.

## Остаточные риски и невыполненные приёмочные сценарии

- Чёрный/белый экран из обращения не воспроизведён, поэтому нельзя объявить его устранённым или объяснить конкретной причиной.
- `QScreen.grabWindow(HWND)` вместе с Qt Paint и проверкой геометрии даёт инструментальное доказательство тестовой отрисовки, но не заменяет визуальное наблюдение пользователем: Windows-композиция и перекрытие окна могут влиять на захват пикселей.
- Длительный native inference/драйвер аудио может пережить ограниченное ожидание shutdown; в таком случае программа не выдаёт ложный статус успешного выхода, но автоматического гарантированного завершения без потери данных пока нет.
- Прямой вызов `QApplication.quit()` сторонним/будущим кодом, минуя `shell.quit()`, остаётся рискованным: `aboutToQuit` запускает асинхронную очистку уже при выходе из event loop. Известный штатный smoke-путь переведён на `shell.quit()`, но внешние/нештатные инициаторы должны проходить отдельную проверку.
- Физическое отключение микрофона, перезагрузка Windows, диктовка/обработка с реальным голосовым вводом и ручная приёмка Computer Use не выполнены. Инъекция `OSError` проверяет программный путь, но не заменяет unplug-тест драйвера.
- Установленная у пользователя сборка 0.2.4 не заменялась исправленной без отдельного согласованного обновления; вместо этого проверена отдельная тестовая установка из финального Inno Setup.
- 30 + 100 запусков предварительно установленного EXE и ещё 100 запусков точного финального установленного EXE прошли без пустых кадров. Нулевые наблюдения в ограниченном тесте не являются гарантией отсутствия всех дефектов.
